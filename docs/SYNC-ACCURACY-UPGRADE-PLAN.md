# 定时点击器：时间同步精度评估与下一步开发预案

评估日期：2026-09-28。代码基线：v0.5.0，提交 `71fde8d`。

本轮工作为代码核查、既有日志分析、合成反例验证和技术预案；没有更改程序算法、运行设置或系统时间，没有将尚未实现的升级效果当成实测结果。

## 1. 结论与推荐顺序

**值得分阶段升级。优先采用“完善采样与误差区间 + 明确容错条件 + 按来源稳健回归 + 内部时钟”，卡尔曼滤波作为后续可比较的估计器。**

可期待的收益是：减少排队尖峰对时间估计的影响，降低重新对时的跳动，提高提前一分钟冻结后的频率预测稳定性，并让误差显示更可信。能否进一步逼近真实 UTC，取决于来源、路径及可验证参考条件，不能只根据滤波曲线更平滑作出判断。

公网 NTP 的固定上下行不对称、共同网络路径和时间源自身偏差，不能由重复采样或卡尔曼滤波唯一识别。若目标升级为可验证的长期 UTC ±1 ms，应把低延迟局域网参考、硬件时间戳和独立测量纳入方案；普通 Windows 的输入调度上限还需要另行评估。

建议顺序：

1. 修补现有区间与统计可信度，补齐回放和诊断数据。
2. 完成受限快速采样、严格的区间容错选择和按来源稳健频率估计。
3. 在相同数据上对比稳健回归与鲁棒卡尔曼，再决定是否替换生产估计器。
4. 如果固定路径偏差主导误差，转向时间源与时间戳基础设施。

## 2. 当前版本已经做了什么

以下以实际代码为准，而非此前开发方案中尚未实现的设想。

| 当前措施 | 实际实现与作用 | 当前限制 |
|---|---|---|
| 内部时钟 | 用 QPC 映射 UTC；系统时间只用于建立初始纪元等。后续由 NTP 校正内部模型 | 已具备基础，不需要重新发明。同步阶段会重新设置模型锚点，尚无完整连续渐调控制 |
| 四时间戳 NTP | 计算时钟偏差和扣除服务器处理时间后的 RTT | 假设近似对称才能把中点当准确偏差；收发时间戳仍在用户态 |
| 协议检查 | 来源/请求匹配、版本、模式、LI、stratum、时间戳和 RTT 检查，KoD 退避，2036 纪元处理 | 当前是未认证基础 NTP，不支持 NTS；并未实施完整闰秒策略分组 |
| 多源与限速 | 默认每源约 10 秒查询，每批最多 6 个并发请求 | 尚无完整的分阶段快速采样与流量预算调度 |
| 来源相关性处理 | 已知运营商别名合组、相同 IP 去重 | 运营商不同不意味着上游参考或网络路径独立；去重主要在估计阶段发生 |
| 样本过滤 | 每源最多 8 个历史样本；异常 RTT 超过历史最小值的 3 倍加 5 ms 时可剔除；用 MAD 估计抖动 | 主估计使用最新通过检查的样本，不是完善的低延迟窗口滤波；MAD 未先去除漂移趋势 |
| 区间一致性 | 每源形成偏差区间，扫描多数重叠区域；多个分离的可行区域会拒绝更新 | 有 Marzullo 类区间扫描的思想，但不是具备明确故障预算和覆盖保证的完整容错实现 |
| 优选与融合 | 按 RTT/2、上游误差、抖动和失败惩罚评分，再选最多 3 个较优来源，以分数平方倒数加权 | 后续裁剪会改变误差覆盖性质；低评分不等于时间正确 |
| 稳健频率拟合 | 使用时间间隔足够长的点对斜率中位数，属于简化 Theil–Sen 类方法 | 窗口与重置策略容易使拟合无法稳定生效；没有经过标定的频率不确定度 |
| 冻结与保持 | 目标前 60 秒停止查询和模型更新，按固定映射执行；误差随样本年龄增长 | 默认 30 ppm 是工程裕量，并非当前硬件的实测残余频率界限 |
| 写回 Windows | 可选调用 SetSystemTime，准备阶段不写回 | 这是对齐本机系统时钟的附加功能，不是定时器的唯一时间基础 |

关键代码：`src/ntp.cpp` 的 `parseNtp/queryNtp`，`src/core.cpp` 的 `combineSources/fitFrequency/ClockModel`，`src/engine.cpp` 的 `updateEstimateLocked/networkLoop/freezeLocked`。

### 2.1 四时间戳是什么意思

令 t1/t4 为客户端发送/收到响应的时刻，t2/t3 为服务器收到/发送响应的时刻：

```text
偏差中点 θ̂ = ((t2 − t1) + (t3 − t4)) / 2
网络往返时间 δ = (t4 − t1) − (t3 − t2)
```

当前 t1、t4 由同一固定 QPC 基准计算，因此改写 Windows 系统时间不会让一次请求中途使用两个不同的本机时基。[1]

### 2.2 当前误差数值的含义

来源区间半径大致包含 RTT/2、上游 root delay/dispersion、服务器精度和工程裕量。代码中还有 0.05 ms 的固定时间戳裕量/下限；它尚未通过本机软硬件标定。

这些是工程估计，不是已经校准的 95% 置信区间。GUI 上“本机 − NTP”接近零，只说明本机时钟与程序估计对齐，不能证明真实 UTC 误差也接近零。

## 3. 本轮发现的具体升级空间

### 3.1 当前来源数量与独立性

读取当前配置时有 6 个域名，但只有腾讯、阿里云两组运营商。既有日志中，`ntp.aliyun.com`、`ntp2.aliyun.com`、`ntp7.aliyun.com` 曾使用相同 IP；`ntp1.aliyun.com` 则出现过多个 IP。

因此，6 个域名不等于 6 个独立时间证据。对于两组来源分歧的情况，没有额外参考就不能判断哪组正确。RFC 8633 建议至少四个独立、多样的时间源。[2]

建议保留 4–6 个多样化候选来源，把一个运营商的多个地址作为可用性备选。还应识别共用 IP、已知共同上游、时间尺度及网络接口；无法确认的独立性明确标记，而不是自动假定。

### 3.2 既有日志能说明什么

本轮读取到 1,244 条既有运行记录，其中 1,204 条为协议有效且 RTT 可用的记录。日志混合了程序会话，缺少会话与模型版本标识；因此这里只按“域名 + IP”分析 RTT，不使用跨会话 offset 证明 UTC 精度。

| 来源/路径 | 样本数 | 最小 RTT | RTT 中位数 | RTT P95 |
|---|---:|---:|---:|---:|
| ntp4.tencent.com / 134.175.254.134 | 188 | 23.123 ms | 29.198 ms | 34.539 ms |
| ntp.tencent.com / 106.55.184.199 | 195 | 25.483 ms | 31.143 ms | 36.968 ms |
| ntp.aliyun.com / 203.107.6.88 | 194 | 39.039 ms | 41.895 ms | 47.640 ms |
| ntp1.aliyun.com / 47.96.149.233 | 57 | 31.270 ms | 32.852 ms | 34.086 ms |

这些数据表明，低延迟筛选有机会减小排队影响。例如第一行由中位 RTT 转向最小 RTT，单次区间的 RTT/2 项可由约 14.6 ms 降至 11.6 ms。

**11.6 ms 不是实际误差的下限。** 它表示在不知道上下行分配时，该次测量允许的偏差范围仍较宽；真实误差可能小得多。多源区间如果互补，还可能进一步缩小范围，但不能预先保证。

### 3.3 当前区间优选存在覆盖问题

本轮直接调用当前 `combineSources` 做了一个无网络、无输入操作的合成验证：

- 真偏差为 0。
- 三个正确来源因路径不对称，测得中点均为 +6 ms；各自区间半径约 10.05 ms，均包含真值 0。
- 加入一个错误来源：也报告 +6 ms，但自称延迟/误差极小，区间半径仅 0.05 ms。

当前结果：

```text
只有三个正确来源：offset = +6 ms，显示误差范围 ±10.05 ms
加入一个错误来源：offset = +6 ms，显示误差范围 ±0.05 ms
```

原因是先通过宽区间的一致性检查，再按质量评分裁剪到低延迟来源，最后仅用裁剪后的来源重新计算误差。加入一个不可信的窄区间后，点估计没有更接近真值，误差条却缩小约 200 倍。

这不是对当前公共服务器发生攻击的判断，而是说明现实现不具备所讨论的拜占庭故障下的区间覆盖保证。**建议优先修补：点估计的优选权重，不能决定安全误差范围。**

### 3.4 频率拟合条件偏脆弱

代码要求至少 6 个融合点且跨度达到 300 秒，但最多只保存 32 个点。在默认每 10 秒更新时，需要接近完整的 31–32 个点才能开始拟合。

此外，只要 `usedSources` 向量变化就清空窗口，即使只是相同来源顺序变化也可能重置。来源较多、分批更新更密时，32 个点甚至可能一直覆盖不足 300 秒。对最新融合值再回归，也会混入来源切换和旧样本按先前频率投影产生的相关性。

建议改为按时间跨度保留原始数据、按来源/路径估计斜率；来源切换主要重置其相位或路径状态，不轻易清空可信的全局频率先验。

## 4. 为什么算法不能消除所有 UTC 偏差

若上行、下行延迟分别为 d_up、d_down，则中点估计包含：

```text
偏差项 = (d_up − d_down) / 2
```

一个不可区分的例子：

| 情况 | 真时钟偏差 | 上行 | 下行 | NTP 得到的偏差 |
|---|---:|---:|---:|---:|
| A | 0 ms | 2 ms | 10 ms | −4 ms |
| B | −4 ms | 6 ms | 6 ms | −4 ms |

两种情况可产生完全相同的四时间戳：t1=0、t2=2、t3=2、t4=12。没有额外信息，任何软件估计器都无法区分它们。重复测量可以让结果非常稳定，却仍稳定地偏了 4 ms。

多源有价值，但共同的最后一段网络、相同 ISP 或共用上游会形成相关偏差，不能把总不确定度除以样本数或其平方根。NTS 能验证来源和报文完整性，仍无法阻止只延迟、不改动报文的时延影响；RFC 8915 明确讨论了这个限制。[3]

## 5. 可选择的升级方案

| 方案 | 主要收益 | 优点 | 缺点/边界 | 建议 |
|---|---|---|---|---|
| A. 修补现有过滤、区间和日志 | 消除过度自信，改善数据质量与可解释性 | 改动较小，可直接复用现有结构 | 主要改善可信度，不保证点估计大幅更接近 UTC | 立即作为下一阶段基础 |
| B. 受限快速采样 + 容错区间 + 按来源稳健回归 | 减少排队噪声、源切换跳动，改善 60 秒预测 | 与当前架构衔接好，诊断和回放容易 | 要明确流量政策、故障模型和时间尺度；固定不对称仍在 | **优先推荐** |
| C. B 的基础上加入鲁棒卡尔曼 | 在线平滑、频率跟踪、保持期不确定度传播 | 适合持续运行与动态噪声 | 调参不当会滞后或极度自信；协方差不含未知偏差时会误导 | 先并行评估，证据充分再启用 |
| D. Windows 软件/硬件网络时间戳 + 可选 NTS | 降低用户态收发戳噪声、提升来源真实性 | 针对明确误差来源改善 | NIC/驱动/系统版本限制；认证本身不修复非对称时延 | 诊断显示主机戳噪声显著时投入 |
| E. 可信局域网 NTP/PTP/GNSS 参考 | 显著缩短并控制授时链路，提供独立验证条件 | 最有希望支撑可验证的 UTC 毫秒级目标 | 增加设备与部署成本；需完整时钟比较链路 | 严格精度要求的后续路线 |

不建议优先做：无限增加相同运营商的域名、无界高频 UDP 查询、单纯加大平滑窗口、用更小数字代替误差预算，或把“更接近 Windows 时间”当成正确性标准。

## 6. 推荐方案 B 的具体设计

```text
来源目录与身份/时间尺度分组
  → 按源流量预算与分阶段采样
  → 时间戳/协议验证、按路径保存原始观测
  → 低延迟过滤与共同纪元投影
  → 明确 f 的容错可行区间
  → 独立计算点估计与误差范围
  → 稳健频率回归 / 可替换 Estimator
  → 程序内部 UTC 时钟
  → 提前 60 秒冻结模型与 QPC 截止时刻
```

### 6.1 采样与路径状态

- 区分启动发现、快速校准、稳定跟踪、路径变化后的重新学习四个阶段。
- 默认每源 10 秒跟踪可保留。只有服务端政策允许时才启用 4–8 个样本的快速窗口；最小间隔服从每源策略。若最小间隔是 10 秒，就不能把 8 包压进 1 秒。
- 公网快速窗口通常是数十秒级；更密集的子秒采样仅用于明确允许的自建局域网服务。处理 KoD、全局/每运营商预算与随机错峰。
- 合并相同实际端点的重复请求。不要只在融合阶段去重，却持续把重复域名当成额外网络观测能力。
- 缓存 DNS 结果并遵守 TTL；在一个健康路径上保留足够历史，不因每轮地址顺序变化就清空整个估计器。IP、接口、地址族和路径代次进入样本标识。
- 按传统 UTC、leap smear 和未知闰秒策略分组，不无条件混合不同时间尺度。无法确认策略时，闰秒调整窗口内退出精度承诺。
- t1 尽量靠近 send，t4 尽量靠近 recv；把取消检查、锁操作和报文准备移出时间戳与系统调用之间，并记录软件夹点开销。改进仅在实测噪声预算中计收益。

chrony 已提供低延迟分位数过滤、median filter、延迟异常检查、频率回归及非对称抖动处理等成熟思路，可作为设计和回放对比参考。[4]

### 6.2 单源区间与低延迟筛选

在一次交换内时钟速率近似稳定、发送/接收延迟非负的条件下，服务器相对客户端的真实偏差受到以下约束：

```text
θ ∈ [t3 − t4, t2 − t1]
```

加入上游误差、时间戳误差、速率误差后向两侧扩展，得到 I_i。其宽度与 RTT 相关，但不是拿一次 RTT/2 当作统计方差。

维护足够的时间历史，优先使用近期较低 RTT 的合格样本，结合 MAD/Huber 等稳健残差处理；不盲信一次最小 RTT，也不让很久以前的最小值永久决定新路径质量。

对跨时刻样本先用频率模型投影到共同 QPC 纪元，并加入预测不确定度，之后才能做区间交叉或比较。直接将漂移时钟不同时间的 offset 当作常数求交，会错误地排除真值。

### 6.3 Marzullo 类选择与故障预算

令 n 为当前合格、独立来源组数量，f 为明确配置的最多错误组数量。计算：

```text
S_f = {x：至少 n − f 个来源区间包含 x}
```

若至少 n−f 个正确来源的区间确实覆盖真值，且故障数没有超过 f，则真值属于 S_f。这是**带前提的区间保证**，不是对 NTP 服务器真实性的无条件证明。

例如以 4 个独立组、容忍 1 个错误组为工程起点，寻找至少 3 个区间支持的区域。来源不足时必须降级，不能把 n 自动缩到 1 后仍沿用“高可靠共识”的标签。

实现要求：

- 扫描端点，正确处理相同坐标、闭区间交点和零宽区间。
- 保留所有合理的可行片段。若 S_f 分成多个区域，不能任意选最短的一段冒充唯一答案；应报告歧义、扩大包络或拒绝精度承诺。
- 区分安全误差范围与操作点估计。质量排序可以选择更好的点，但不能把 f 容错形成的范围缩成一个自称高精度的来源。
- n、f、来源组及被排除原因进入日志。区间端点所用的服务器误差声明、身份与独立性假设必须可审计。
- 不能按重复样本数量增加票数，也不能把域名数量当成独立组数量。

若点估计为 θ̂，覆盖整个可行集合的误差至少应按 `E_safe = max(|θ̂ − inf(S_f)|, |sup(S_f) − θ̂|)` 计算，再叠加后续保持误差。只有 θ̂ 位于包络中点时，才可直接使用包络宽度的一半。

这里解决的是客户端的容错区间估计，不是节点之间的拜占庭共识协议。不要机械套用“3f+1”并据此宣传所有条件下可获得正确 UTC；来源区间是否可信、是否相关以及结果是否唯一仍须检查。

### 6.4 稳健回归作为首选 Estimator

每条来源路径建模：

```text
offset_i(t) = a_i + ν × (t − t0) + noise_i(t)
```

a_i 吸收该来源相位与固定路径偏差，ν 是共享的 QPC 到 UTC 速率偏差。固定 a_i 不会影响同一路径内的斜率，但路径改变会，因此要识别变点。

建议先采用按来源的 Huber 加权线性回归，或明确实现的 Theil–Sen 估计作稳健基准，再跨独立来源组合频率。按时间跨度保留约 10–30 分钟数据，样本数量与轮询间隔一起决定，而不是固定 32 点却要求 5 分钟跨度。

不因优选列表顺序变化清空频率历史。路径改变时重置该路径的截距/窗口，保留但放宽全局频率先验；各来源斜率分歧显著时报告异常。

此模型不能辨认 a_i 中哪一部分是绝对 UTC 偏差。把各 a_i 均值强制设零只是一种先验，不是从网络观测中获得了真值。

### 6.5 内部时钟与冻结

继续使用：

```text
U(q) = U0 + (1 + ν) × (q − q0) / QPC_frequency
```

当前内部时钟可以复用。新增独立时钟模式，关闭 Windows 写回即可减少系统时间跳变、权限需求和与系统校时服务的互相影响；**这一变化本身不消除 NTP 误差**。

保留现有系统写回开关，不擅自覆盖老用户选择。输入到管理员权限软件仍可能需要相应权限，这与是否写系统时间是两个问题。

保持既有“提前 60 秒冻结”的默认语义：停止采样/校正，固定一次任务的模型与截止点。使用学习到的频率继续预测，并在冻结前检查预测预算：

```text
E_hold(T) = E_phase + E_pending_correction
            + frequency_error_bound × T + model_margin(T)
```

30 ppm 在 60 秒对应 1.8 ms；若后续实测能把残余频率误差界限降至 2 ppm，则对应项约为 0.12 ms。这只是计算示例，是否达到 2 ppm 要由数据与独立参考验证。

若引入连续渐调，应区分最佳 UTC 估计和对外单调输出。尚未消化的相位差必须计入误差；冻结时不能把暂时的追赶速率继续保持一分钟而造成过冲。优先在冻结前收敛，未收敛则按质量门槛降级。

## 7. 卡尔曼是否值得加入

值得作为方案 C 的候选，不建议作为第一步直接替换。

一个合理的两状态模型为：

```text
x = [offset, frequency_error]ᵀ
F(Δt) = [[1, Δt], [0, 1]]
z = [1, 0] x + source_bias + measurement_noise
```

频率随机游走可用与 Δt³/3、Δt²/2、Δt 成比例的过程噪声矩阵描述，再通过数据估计参数。量测噪声根据低延迟样本残差、服务器质量和路径状态调整，不能直接将 RTT 当作高斯标准差。

必要配套：

- 对创新残差做鲁棒门控，拒绝尖峰；对真正路径/时钟变化有重置或噪声膨胀机制。
- 模型协方差与系统性偏差预算分别维护，不能用小协方差掩盖固定不对称。
- 多来源共同路径产生相关噪声，应采用分组/相关性模型或保守上限，不能按独立测量反复叠加置信度。
- 如果同时估计各来源 bias，必须说明不可辨识性及采用的先验，不能声称由模型自动恢复了唯一真 UTC。
- 使用当前数据滤波和预测；离线使用未来数据的平滑器只可用于分析，不能拿其效果冒充在线触发前就能获得的精度。

推荐让回归与卡尔曼先使用同一批样本并行计算，后者只记录结果，不控制真实任务。只有在保持期预测、覆盖率和异常恢复都显著改善时，才切换默认估计器。

## 8. 硬件时间戳、NTS 与外部参考

Windows 的 packet timestamping 支持查询网卡能力；软件时间戳由驱动使用内核侧 QPC 生成，硬件时间戳来自 NIC 自己的时钟。应先探测设备与驱动能力，不能假定普通网卡已经支持。[5]

候选 API 包括 SIO_TIMESTAMPING、GetInterfaceSupportedTimestampCapabilities 和 CaptureInterfaceHardwareCrossTimestamp。硬件戳必须通过交叉时间戳映射到 QPC；不能直接混合两个时钟域。不同接口有不同的系统版本要求，应运行时检测并提供回退。[5–7]

NTS 优先采用成熟实现/密码库，补齐身份验证，不自行设计密码协议。它解决真实性，不等同于解决时延不对称。启用 TLS 时还要处理初始日期错误和证书时间校验，不能通过关闭证书验证来“解决”校时启动问题。[3]

若使用局域网 GNSS/NTP/PTP 参考，应列出参考设备、可追溯性、NIC/驱动和校准链路。软件 PTP 并不自动比良好 NTP 更准，普通 USB 串口收到 PPS 的时间也不能直接当作精密真值。

## 9. 验证方式与继续/停止条件

### 9.1 先补日志与可重复回放

增加 session_id、软件/模型版本、QPC 原始收发值、路径标识、来源组、过滤结果与原因、n/f/共识区间、频率与不确定度、待消化相位差、冻结预测、系统写回模式等字段。

每种算法用同一份原始记录回放，避免网络时段不同使 A/B 结果无法比较。现有日志仍可描述 RTT，但不足以单独重建所有模型状态或证明 UTC 偏差。

先在相同查询预算下比较算法，并同时报告请求数量、CPU/功耗和收敛时间；额外增加采样带来的收益单独记录。

### 9.2 已知真值的合成实验

覆盖对称/不对称路径、共同末段偏差、排队尖峰、乱序/丢包、路径变化、晶振漂移与温度变化、错误服务器、同运营商别名、来源失联和闰秒策略不一致。

在故障预算和正确区间假设成立时，检查真值始终在所报告的容错范围内。预算不成立时应明确降级，不能通过删掉失败样本而得到好看的精度数字。第 3.3 节的反例作为必须通过的回归用例。

### 9.3 专门评估 60 秒冻结预测

每个评估时刻仅使用此前的数据拟合，预测 60 秒后；后续样本留作验证，禁止未来数据泄漏。报告带符号偏差、绝对误差分位数、最大值、重新收敛时间和误差包络覆盖情况。

公共 NTP 的未来样本仍有网络噪声，只能作为有限验证。要声明 UTC 绝对精度，必须使用独立、可追溯且误差已知的参考链路。不要用已被本程序改写的 Windows 时钟、同一批授时源或等待定时器基准自证 UTC 准确。

连续观察 24–72 小时，使用保留时间段/保留来源评估；重叠窗口高度相关，应按时间块统计置信范围。少量样本或大量相关样本不能支撑可靠的 P99.9 声明。

### 9.4 建议的阶段门槛

- A 阶段：修补后通过区间覆盖和故障反例；新日志能够重现一次校时与冻结决策。
- B 阶段：在预先固定的模拟场景及留出时间段上，重新对时跳变和 60 秒预测 P95 目标改善至少约 30%，同时误差覆盖不恶化、正常同步可用率不下降。30% 是立项验收建议，不是本轮实测收益。
- C 阶段：只有在 B 的基础上仍获得稳定、可重复的额外收益，并能解释协方差覆盖与变点恢复，才引入卡尔曼默认控制。
- 如果低 RTT 分布已很稳定、进一步滤波收益很小，而独立参考显示固定偏差主导，则停止继续堆叠估计器，转向方案 D/E。
- 若没有独立参考，最终结论最多是“更稳定、预测更好、估计范围更合理”，不能升级为“已证明 UTC ±1 ms”。

## 10. 现有软件的升级路径

| 阶段 | 主要改动 | 交付物 |
|---|---|---|
| M0：基线与可观测性 | 扩展 Sample/日志，建立录制与回放，区分统计抖动和系统性预算 | 基线报告、数据格式、合成场景 |
| M1：可信区间 | 独立的 IntervalConsensus 模块、显式 f、端点处理、歧义检测；点估计和范围分离 | 修复反例的核心版本及状态展示 |
| M2：采样与保持 | SourceTracker/采样预算、按路径过滤、长时间窗稳健回归、独立内部时钟模式 | 推荐的首个算法升级版及 60 秒预测报告 |
| M3：估计器对比 | IClockEstimator 接口，回归与鲁棒卡尔曼并行回放/记录 | 决定是否采用卡尔曼的对比报告 |
| M4：条件增强 | NIC 能力探测、网络时间戳、NTS、局域网参考接入 | 面向严格 UTC 目标的可验证模式 |

保留 `Engine` 的预约/冻结/取消和 `DeadlineScheduler` 执行路径，新增采样和估计模块从原始观测产生不可变时钟快照。避免在关键输入提交段加入回归、滤波、网络或文件工作。

建议下一次开发范围先定为 **M0–M2**。这是对当前实现缺口有针对性的升级，成本和可验证性优于直接引入完整卡尔曼控制。精度承诺随测量证据升级，不随算法名称升级。
