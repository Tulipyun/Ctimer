# Ctimer：Windows x64 精确定时输入程序开发方案

日期：2026-09-28。本文为开发方案，已按用户审定修订：C++20 + Win32；可编辑来源列表；毫秒严格为三位；执行前 60 秒冻结校时；完整 down/hold/up 操作以 down 为定时起点。v0.1 的实际交付范围与测试结果见项目 README 和测试报告。本文中的性能数字仍是设计目标、参数初值或计算示例，不是实测结果。

## 1. 推荐方案与可实现边界

采用 **C++20 + 原生 Win32 GUI + Winsock NTP 客户端 + QPC 单调时钟 + 高分辨率等待定时器 + SendInput**，最终交付 Windows x64 的 `Ctimer.exe`。程序内部维护由多个网络时间源校准的 UTC 时钟，任务按该时钟执行；修改 Windows 系统时间作为可选功能。

需要把三个指标分开：

| 指标 | 含义 | 能否单靠本程序控制 |
|---|---|---|
| UTC 校时误差 | 程序时钟与可追溯 UTC 的差距 | 可以估计和改善；公网 NTP 存在无法单独识别的路径不对称 |
| 调度与提交误差 | 程序在何时调用 SendInput、调用何时返回 | 可以显著优化并实测，但普通 Windows 不提供硬实时上限 |
| 目标响应误差 | 目标软件何时读取输入、执行操作或发出网络请求 | 受目标软件、消息循环、帧率和网络等影响，必须单独测量 |

**第一版以“在目标 UTC 时刻提交按下事件”为核心目标。** 不把 GUI 显示到毫秒、计时器使用 100 ns 单位或 QPC 分辨率高，等同于实际误差达到该量级。

公网条件下可以追求毫秒级，不能承诺在任何网络和负载下始终 ±1 ms。微软也把 1 ms 级系统校时放在特定高精度环境条件下讨论。[1–5] 如果最终验收要求每次都在严格的 ±1 ms 内，需考虑局域网硬件时间源、硬件时间戳，甚至专用实时硬件输入设备。

推荐同时支持两种运行模式：

- **尽力准点模式**：显示当前估计误差，用户可在精度不足时仍执行任务。
- **精度门槛模式**：用户设定误差预算；校时不确定度和本机调度统计指标不满足条件时，拒绝进入待执行状态。这个门槛是有前提的质量检查，不是 Windows 硬实时保证。

## 2. 语言、GUI 与发布形式

| 方案 | 适用性 | 本项目取舍 |
|---|---|---|
| C++20 + Win32 | 直接调用 Windows API，无 GC，可预分配整个执行路径；可制作便携 exe | **首选**；界面开发量较大，但本项目界面规模可控 |
| C++20 + Qt Widgets | GUI 开发更快，核心精度可以相同 | 可替代；增加部署依赖及许可处理，第一版暂不采用 |
| Rust + Windows API | 无 GC，内存安全优势明显 | 同样能胜任；Windows GUI 与依赖组合需要额外评估，不因语言自动获得更高精度 |
| C#/.NET + WPF | GUI 效率高 | 若采用，应把关键执行放入原生模块；纯托管关键路径增加暂停因素 |
| Python、Electron、AutoHotkey | 适合原型、脚本或普通自动化 | 不作为本项目最终精确定时核心 |

语言选择减少的是可控的软件开销，不能消除 DPC/ISR、线程抢占、驱动阻塞或网络误差。

工程使用 MSVC、CMake、Windows SDK，Release x64；GUI 使用 Win32/Common Controls，中文界面、Unicode、Per-Monitor DPI Awareness V2。首批验证 Windows 11 x64，并在有实际需求时验证 Windows 10 22H2 x64；所需高分辨率等待定时器 API 自 Windows 10 1803 提供。[3]

发布采用静态 C/C++ 运行库 `/MT`、系统自带 DLL，主程序无需安装 Python、.NET 或 Qt。源列表与默认配置可嵌入 exe；配置、日志写入用户目录。测试探针和系统校时辅助入口可以复用同一 exe 的命令行模式。代码签名属于正式发布流程。

## 3. 程序结构与线程职责

```text
Win32 GUI / 配置与任务编辑
    ├── SourceCatalog        时间源目录、分组、DNS、限速和健康状态
    ├── NtpSampler           多源采样、原始报文验证、收发时间戳
    ├── ClockEstimator      滤波、共识、偏差/频率估计、误差预算
    ├── DisciplinedClock     网络校准的单调 UTC 时钟和模型版本
    ├── TaskCompiler        把点击/按键/循环转成完整事件时间表
    ├── DeadlineScheduler   UTC 截止时刻转换、等待、末段精确定时
    ├── InputBackend        SendInput、按下状态、取消与释放
    └── Diagnostics         原始采样、执行记录、探针、统计报告
```

线程分工：GUI 线程只显示和编辑；网络线程执行有限并发 UDP 查询；估计线程维护时钟；专用执行线程只等待和提交预编译输入；日志线程异步落盘。原始样本和模型快照都有版本，使用预分配队列及不可变快照交换数据。

关键执行段禁止 DNS、网络请求、文件写入、脚本解释、动态分配和等待 GUI 锁。GUI 卡顿不应阻止已布置的任务。

任务状态明确为：`编辑 → 检查 → 待执行 → 执行 → 完成/取消/错过/失败`。重启后不自动补发已经错过的输入。

## 4. 时间源如何自动获取与维护

### 4.1 发现和选择

维护一个随程序发布、可更新的时间源目录，存储域名、运营者分组、服务策略、闰秒策略、认证能力和探测结果。启动后自动 DNS 解析与探测，选择当前网络下适合的源；允许用户添加可信的局域网服务器。

首选保持 **4–6 个源、尽量至少 4 个独立运营者或上游组**。RFC 8633 建议至少四个独立且多样化的时间源。[7] 多个域名解析到同一 IP、同一运营者的多个节点，以及共享上游的源，不能简单视为多张独立选票。来源、RefID 和可获得的网络信息用于识别相关性，但不能保证路径真的独立。

可纳入候选目录的已核查公开服务：

| 候选 | 用途与限制 |
|---|---|
| `time.cloudflare.com` | 官方公开 Anycast NTP；不进行 leap smear，实际可达性与 RTT 需测量。[10] |
| `ntp.nict.jp` | NICT 官方公开服务，可作为亚洲地区候选；服务器自身标称精度不能当作客户端精度。[12] |
| `time.nist.gov` | NIST 官方公开服务，适合作为多样化备选；地理距离可能使其不适合低误差主源。单服务器查询不得快于 4 秒一次。[13] |
| NTP Pool 厂商专用域名 | 补充地区节点；公开分发程序默认使用前申请 vendor zone，不能直接把公共 pool 域名当作批量产品默认值。[11] |
| 用户配置的本地 NTP/GNSS/PTP 网关 | 对严格精度最有价值；明确来源、校准状态和可用轮询频率 |

面向国内网络，发布前另外核实国内运营者公开服务的当前域名、使用规则、闰秒策略和可达性，加入目录。此次未充分核实的国内域名不作为已经确认可用的默认项。上述国际源也不意味着在用户网络上均可访问。

源目录负责“找到候选”，实测负责“选出可用源”。不依靠运行时抓取随机网页列表，也不长期硬编码服务器 IP。DNS 按 TTL 更新；地址、接口或路由环境变化时重新建样本窗口，避免混合不同路径。

### 4.2 闰秒和时间标准

内部统一使用 UTC，界面默认按 Asia/Shanghai（UTC+08:00）显示。时区只是显示和输入解释，不参与网络校时算法。

Google Public NTP 使用 leap smear，闰秒附近可与 UTC 相差接近 0.5 秒；Cloudflare 使用非 smear 策略。[9–10] **不能无条件把两类源混合平均。** 首版选择传统 UTC 来源组，未知策略源只作辅助观察；闰秒附近若不能确认一致性，退出精度门槛模式。

首版不接受 `23:59:60` 任务，也不支持跨已知闰秒调整窗口的精确任务；待独立完成闰秒/TAI 时间轴设计和测试后开放。时间尺度、来源策略和限制应写入任务记录。

### 4.3 快速对时与限速

- 启动/手动对时：有限并发探测选定的 4–6 个源，随后分轮收集有效样本；每源仅保留少量在途请求。
- 只有源策略允许时，使用类似 iburst 的 4–8 次启动采样；间隔服从每源限制，不能统一写成 1 秒一次。对 NIST 至少 4 秒，对未确认允许快速采样的源采用更保守间隔。
- 常态自动对时初始采用每源 64–256 秒的间隔，并加入随机错峰；依据残余漂移、样本年龄和服务政策调整。频繁轮询只用于允许的自建局域网源。
- 手动按钮复用当前采样任务，不绕过令牌桶、不重置限速；任务即将执行也不能借机集中冲击公共服务。
- KoD `RATE` 触发退避，`DENY/RSTR` 停用该源；超时、丢包和 DNS 失败设置冷却与有限重试。绝不通过换 IP 规避限速。

在允许启动采样且网络正常时，争取约 15–45 秒形成首个偏差估计；频率稳定估计通常需要持续数分钟甚至更久。GUI 显示“发现、采样、共识、漂移学习”各阶段和真实完成量，不承诺固定时间达到 1 ms。

## 5. 单次 NTP 计算与报文质量控制

### 5.1 四时间戳算法

使用 NTPv4 client/server 模式，记录：

- `t1`：本机发送请求的时间。
- `t2`：服务器接收请求的时间。
- `t3`：服务器发送响应的时间。
- `t4`：本机接收响应的时间。

其中 `t1、t4` 必须来自**同一个版本**的 QPC→时间映射，禁止发送时读一次系统时间、接收时再读可能已被校正的系统时间。

```text
offset θ = ((t2 - t1) + (t3 - t4)) / 2
network RTT δ = (t4 - t1) - (t3 - t2)
```

`θ > 0` 表示服务器比本机参考时钟快。`δ` 扣除了服务器处理时间，不能用 ping RTT 直接替代。[6]

时间戳采集在 `sendto` 前和 `recvfrom` 成功后尽量紧邻系统调用；另外记录调用前后 QPC 夹点以观察软件开销。用户态时间戳包含内核排队和线程唤醒误差，必须进入误差预算。第二阶段研究受支持 NIC/驱动上的 Windows 网络时间戳 API，不能把用户态采样称作线缆到达时间。

第一次只用系统时间作日期/纪元启动提示，随后由网络确定绝对时间。对请求使用唯一匹配标识/时间戳；传输层的匹配值和本地精确采样分开保存，若为唯一性扰动字段，不直接拿扰动后的值参与估计。

### 5.2 必须实现的校验

- 验证长度、字段边界、版本、服务器模式、来源地址和端口，匹配 originate 字段及在途请求，拒绝重复/重放/迟到响应。
- `LI=3`、无效 stratum、缺失时间戳、明显异常服务器处理时间、不合理 root dispersion 等均拒绝；stratum 0 按 KoD 处理。
- 检查 RTT、offset 和时间戳一致性；负 RTT 超出量化误差则拒绝，不能强行裁成零并赋予最高权重。
- 支持 NTP 32 位秒字段的 era 展开，测试 2036 回绕。若本地日期错到无法确定纪元，显示日期不可信并停止精确模式，使用明确可信的启动日期或管理员配置恢复。
- 长报文的扩展字段必须安全解析或按明确策略拒绝；未来 NTS 不能依赖“所有 UDP 包都恰好 48 字节”的假设。

## 6. 从多个样本获得准确且稳定的时间

### 6.1 先做每源滤波

每源维护最近约 8–32 个有效样本，记录原始四时间戳、RTT、offset、服务器质量、模型版本和采样年龄。

1. 先执行协议和健康检查。
2. 跟踪该路径的低 RTT 基线，使用 RTT 分位数和 MAD 检查异常排队延迟。
3. 借鉴 NTP clock filter，从近期低延迟样本得到相位估计；样本足够时做稳健拟合，而非全体算术平均。[6,14]
4. 用残差的稳健尺度估计 jitter。最低 RTT 样本也必须通过时间一致性检查，不能无条件信任。
5. 限制最旧样本年龄；新路径、新地址、恢复联网后重建基线。阈值从回放和实测定标。

高 RTT 阈值用于剔除坏样本，低于阈值只表示可以参与估计，不表示达到毫秒精度。高 stratum 可能意味着更多层级，但不能仅按 stratum 大小排序，更不能直接用 stratum 作为精度。

### 6.2 使用误差区间选择一致来源

将样本投影到共同 QPC 纪元后，对每个来源生成一个包含不确定度的区间：

```text
I_i = [θ_i - E_i, θ_i + E_i]

E_i ≈ δ_i/2 + max(root_delay_i, 0)/2 + root_dispersion_i
      + 软件时间戳误差预算 + 抖动裕量 + 样本老化误差
```

这是依据 NTP root distance 思路构造的工程误差包络，并非已校准的 95% 置信区间。它依赖服务器诚实、上游误差声明合理等前提；实现需避免重复计算已经计入 dispersion 的分量。[6]

以独立来源组为投票单位，采用 RFC 5905 所述选择/聚类思路寻找多数一致区间。精度门槛模式要求至少三个独立来源组一致，通常从四个或更多组中选择；不把单个存活源的 1/1 一致视为多源共识。单源或双源只能进入标明限制的降级状态。

聚类后对幸存源进行带权稳健融合，例如权重与 `1/(jitter² + floor²)` 和 root distance 相关，并设置单运营者权重上限。对存在多个不相交的合理共识区间，判为来源分歧，不强行挑一个好看的平均值。

估计值可以通过多源融合变得更平滑，但**网络不对称误差不能除以 √N**。最终误差范围保留各来源共同路径、系统性误差及合理共识区间的包络，不把样本数量当作绝对精度的证据。

### 6.3 网络不对称的不可识别部分

设上下行延迟为 `d_up、d_down`，NTP 偏差估计包含：

```text
offset_bias = (d_up - d_down) / 2
```

例如上行 2 ms、下行 10 ms，RTT 是 12 ms，但估计时钟会有约 -4 ms 的系统性偏差。即使重复测量数千次、抖动几乎为零，这个偏差也不会因此消失。

措施包括：选择低延迟且不同运营者的路径、优先有线网络、剔除排队尖峰、观察路径改变、避免对少量 RTT 变化过度拟合。高级版可估计随负载变化的非对称抖动，但固定单向延迟差仍不能仅从普通 NTP 往返消息唯一求出。

因此界面同时显示：**重复性/jitter、NTP 估计误差包络、独立参考实测偏差**。没有独立参考时，最后一项明确写“未验证”。

### 6.4 估计晶振频率并保持单调

将 QPC 计数差转换为秒：`x = (q - q0) / QueryPerformanceFrequency()`，用仿射模型表示网络 UTC：

```text
UTC_est(q) = a + (1 + ρ) × x
```

`a` 是校准时刻 UTC，`ρ` 是频率偏差，按 ppm 显示。使用数分钟至数十分钟的滑动窗口、带权回归及稳健残差处理估计相位和频率；对非同时采集的不同来源先做时间投影，避免将网络偏差变化误判为晶振漂移。

首批样本优先确定相位，积累足够时间跨度才提高频率估计置信度；路径跳变时不立即学习为频率变化。保存长期频率估计只能作为下次启动的先验，不能直接标记已同步。

维护两个内部概念：网络拟合得到的最佳时间估计，以及用于显示/调度的受控单调时钟。首次同步且无待执行任务时允许直接建立基准；运行中小幅校正采用连续渐调，避免时间倒退。二者的待消化相位差计入当前不确定度并在 GUI 展示，不能通过平滑掩盖真实偏差。

渐调速率设置明确上限，例如以 500 ppm 作为待验证初值；模型更新在锚点连续。遇到大偏差，取消精度门槛任务、重新校时，不在最后时刻跳动截止时间。

### 6.5 失联和漂移预算

断网后依靠 QPC 和已学习频率保持时间，同时增长误差包络：

```text
E_clock(age) = E_at_sync + E_pending_slew
               + residual_frequency_bound × age + model_margin(age)
```

例如尚未补偿的 20 ppm 相当于每秒 20 μs，一分钟累计 1.2 ms。有效保持时间由剩余预算决定，不固定写成“断网十分钟仍然精确”。

休眠/恢复、虚拟机迁移、网卡切换及大幅时钟异常后重新评估；首版恢复后暂停待执行任务并重新同步。QPC 的时间间隔测量不随系统时钟人工修改跳变，但不能因此假设休眠跨越的任务仍可照常执行。[2–4]

## 7. 是否把网络时间写入 Windows

默认只校准程序内部时钟，不需要系统校时权限，也不会与 W32Time 争夺系统时钟。始终显示“程序 UTC − Windows UTC”，系统时间读取使用精确系统时间 API 配合 QPC 夹点。

可选“校准 Windows 系统时间”功能：通过单独提权入口申请 `SE_SYSTEMTIME_NAME`，调用 `SetSystemTime`，输入 UTC。[15] 写入前重新计算当前网络时间，不使用数秒前样本的时间值。写入后夹点读回，报告误差和不确定度。

一次 SetSystemTime 不能维持长期精度，其结构和调用过程也不提供亚毫秒校时保证。首版不循环调用它来驯服系统时钟，不默认停用 W32Time；持续驯服系统时钟留给独立、明确配置的后续模式。待执行任务期间禁止本程序主动改系统时间，外部系统时间跳变单独记录，内部 QPC 任务不因此重定时。

## 8. 如何在目标时间提交输入

### 8.1 把 UTC 目标转换为 QPC 截止时刻

用户输入先转换为唯一的完整 UTC 目标 `T`，再按受控时钟模型反求 `q_deadline`。任务距离较远时可随模型更新修正映射；在执行前 **60 秒** 停止同步，固定模型版本和截止计数。若创建任务时已不足 60 秒，立即冻结。冻结后晚到的查询结果也不能应用；完成或取消后由用户手动恢复同步。

冻结期间的漂移、尚未收敛的相位差和模型年龄仍计算进误差。若得到新的明确异常或预测预算超限，取消精度门槛任务；不静默移动截止时间。临近时不发起新的校时突发、图表重算或日志刷盘。

### 8.2 分段等待

1. 距离较远时采用事件等待，可同时响应取消。
2. 接近截止时使用 `CreateWaitableTimerExW(CREATE_WAITABLE_TIMER_HIGH_RESOLUTION)`，设置**相对等待时间**、单次触发和零主动容忍延迟。
3. 提前一小段保护时间唤醒；建议从 0.5–2 ms 范围实验，按本机唤醒延迟分布确定。
4. 最后一段循环读取 QPC，达到截止计数后立即调用 SendInput；自旋使用适当处理器提示并检查原子取消标记。

保护窗口来自测量，过小会错过截止，过大会占用 CPU。一次任务短暂占用一个核心可接受；高频重复任务需限制连续自旋预算并报告能力限制。

使用 QPC 控制最终截止，而非依赖 Windows 绝对时间定时器，因为后者会受系统时间调整影响。[4] 定时器的 100 ns 参数单位不意味着 100 ns 调度精度。

优先测试高于普通线程的执行优先级；经测量选择 High/MMCSS 等策略，不默认使用 `REALTIME_PRIORITY_CLASS` 或全程最高优先级。CPU 亲和性仅作为实验选项，现代 QPC 通常无需固定核心。[2] 不通过修改 HPET/启动项作为默认优化。

`timeBeginPeriod(1)` 不是主要方案，也不会提高 QPC 本身精度。若兼容路径需要它，严格配对 `timeEndPeriod`，并测试最小化/遮挡及 Windows 11 的相关限制。[16]

### 8.3 明确定义“按下”

键盘一次按键分成 key-down 和 key-up；鼠标一次点击分成 button-down 和 button-up。默认目标时刻指 **down 事件的提交调用**，释放在设置的持续时间之后，例如按住 20 ms。

SendInput 无法指定“未来硬件执行时间”，`INPUT` 中的 time 字段也不是预约执行参数。按下和释放需要按时间表分别提交；要保持 20 ms，不能把 down/up 放进同一批立即提交。

组合键默认以第一个 down 为序列开始；若需要 F8 主键在 T 时刻按下、Ctrl 提前准备，应在预览中明确显示 Ctrl 的提前事件，不能悄悄提前操作。一个 SendInput 批次内部按顺序插入，也不等于多个事件有各自可验证的精确执行时间。[5]

输入后检查实际插入的事件数量，部分成功视为失败并处理已按下状态。记录 `QPC_before_SendInput` 和 `QPC_after_SendInput`，不能把“函数返回时间”谎称为目标应用收到时间。

默认不根据历史平均值提前调用来补偿，因为这可能造成早发。可以提供显式实验补偿参数，但必须显示其适用参考点和提前风险。程序最多保证相对其冻结 QPC 截止不主动早发；相对真实 UTC 是否提前还取决于校时误差。

### 8.4 Windows 输入限制与恢复

- SendInput 受 UIPI 完整性级别限制；普通权限不能向更高权限程序注入。检测并说明，需要时用户自行选择同等权限运行，不能把失败显示为已执行。[5]
- 键盘输入指向当前前台窗口；鼠标按屏幕坐标/光标位置进入系统输入流，不能承诺向任意后台 HWND 精确投递。可选锁定目标窗口身份，临近执行检测不匹配则取消；检查和注入之间仍存在竞争窗口。
- 支持虚拟键和扫描码模式；记录键盘布局和扩展键。组合键前检查物理按下状态，避免干扰用户正在按住的键。
- 点击支持当前位置及预设位置；固定位置使用完整虚拟桌面坐标并处理 DPI、多屏和负坐标。若提前移动鼠标，提前动作必须出现在时间表中。
- 注册全局停止热键，例如 Ctrl+Alt+F12；取消时停止后续事件，并尽力释放本程序持有的按键/鼠标按钮。进程崩溃后的释放不能仅靠析构保证，独立看护进程可作为后续增强。
- 锁屏、UAC 安全桌面、休眠等不作为支持的精确定时环境。待执行期间可按设置保持系统唤醒；会话变化时取消并报告。

## 9. 时间输入和简单脚本语义

### 9.1 时间输入

提供两种明确模式：

- 当前小时：`MM:SS.mmm`，例如 `59:59.123`。
- 完整时间：日期 + `HH:MM:SS.mmm` + 时区，适合跨小时和长期预约。

原需求中的 `1234` 毫秒已由用户澄清为笔误。毫秒字段严格采用 `000–999`，拒绝四位毫秒及越界输入，不执行进位或跨秒转换；例如合法输入为 `59:59.123`。进入待执行前显示完整日期和时间，避免只显示分钟秒。

默认已过的“当前小时”时间报错，不自动立即执行或暗中排到下一小时；提供独立的“下一次出现”选项。时区发生变化后保留已经确定的 UTC 目标；存在夏令时重叠或缺失的本地时刻必须显式解决。

### 9.2 动作表与脚本

首版支持：单键、组合键、鼠标左/右/中键、按住时长、重复次数、起点间隔、延时、键鼠混合序列。优先提供动作表，并保存为 JSON；可配一个很小的文本语法：

```text
key F8 hold=20ms
wait 80ms
repeat 3 every=100ms {
    click left hold=10ms
}
```

这里 wait 从上一动作结束算起，every 表示相邻循环**开始到开始**的间隔。上例相对任务目标 T 的完整表为：F8↓ 0 ms、F8↑ 20 ms，鼠标↓ 100/200/300 ms、鼠标↑ 110/210/310 ms。

编译阶段展开成 `T + Δ_i` 事件表，执行阶段不逐条解释脚本。每个事件以 T 为固定锚点，禁止“执行完再 Sleep(interval)”造成误差累积。校验重复次数上限、总时长、重叠冲突和间隔是否小于动作持续时间。

事件迟到策略分开处理：错过容忍窗口的 down 默认跳过/停止并报告，不批量补发；为避免卡键，已提交 down 对应的 up 仍应尽快释放。容忍窗口可设置，所有错过都计入统计。

首版不运行任意 Python/PowerShell/JavaScript 或无限循环；后续如扩展复杂脚本，解释器只生成计划，不进入精确定时路径。

## 10. GUI 首批功能

主界面包含以下区域：

| 区域 | 内容 |
|---|---|
| 当前时间 | 网络校准时间 `YYYY-MM-DD HH:MM:SS.mmm`、时区、Windows 时间差、同步状态 |
| 质量摘要 | 活跃/独立来源数、估计误差包络、jitter、漂移 ppm、最后同步时间、剩余保持预算 |
| 来源明细 | 域名/IP、运营者、stratum、RTT 最小/中位、offset、jitter、root dispersion、使用/剔除原因 |
| 对时控制 | 手动对时、自动对时、来源管理、阶段进度和样本数、可选系统校时 |
| 定时输入 | 时间模式、完整时间预览、动作类型、按住时长、重复/间隔、混合事件表 |
| 执行控制 | 质量门槛、待执行、取消、倒计时、目标窗口、全局停止热键 |
| 测试与日志 | 本机定时基准、输入探针、执行误差统计、CSV/JSON 导出 |

刷新时间显示建议 30–60 Hz；文本包含毫秒不代表屏幕每毫秒更新。调度与 GUI 刷新完全独立。

同步状态使用“未校准、采样中、多源一致、保持运行、来源分歧、质量不足”等明确标签。精度估计使用例如“估计 ±4.2 ms，UTC 独立验证：未完成”；不要将低 jitter 用绿色 `±0.1 ms` 冒充绝对准确度。

进度只对有限工作计百分比，例如“已收到 18/24 个计划样本”；频率收敛显示观察时长与残差，不制作必然达到 100% 精度的倒计时。

## 11. 测试与可验证性

### 11.1 数学、协议和状态机测试

为核心模块建立可注入的虚拟 QPC、模拟网络和输入后端；测试无需真实点击：

- 已知偏差和频率，发送/接收延迟可控，验证 θ、δ、符号、单位、转换和溢出。
- 对称延迟、固定不对称延迟、排队尖峰、乱序、重复包、丢包、KoD、恶意时间戳、源切换。
- 多数正确/少数错误、两个来源阵营、同运营者多 IP、系统性共同偏差；确保不产生虚假的高精度判定。
- ±ppm 漂移、频率改变、断网保持、过期样本、模型连续性和冻结窗口。
- 系统时间向前/向后跳、休眠恢复、跨小时/跨日、2036 NTP 回绕、闰秒拒绝路径和无效毫秒拒绝。
- 混合序列绝对锚定、部分 SendInput 成功、取消释放、重启不重放、迟到不补发。

已知不对称测试应证明“算法诚实保留偏差风险”，不能要求没有额外信息时估计器神奇恢复真值。

### 11.2 本机调度基准

先用空动作测量等待与调用前误差，再用 `Ctimer.exe --probe` 打开的自有测试窗口接收 F8/鼠标事件。探针使用相同机器的 QPC，程序通过 `dwExtraInfo` 任务标记关联事件；低级输入 hook 只在诊断模式启用。

分别记录：

```text
J_call    = SendInput 调用前 QPC - 计划截止 QPC
C_call    = SendInput 调用后 QPC - 调用前 QPC
J_hook    = 探针低级 hook QPC - 计划截止 QPC
J_handler = 测试窗口处理事件的 QPC - 计划截止 QPC
```

hook 测量也包含 hook 线程调度延迟；窗口消息处理时间不是硬件到达时间。这些测试验证本机调度和可观察输入流程，**不能证明绝对 UTC 准确度**。

每个主要场景至少收集 10,000 次受控测试事件，覆盖不同未来间隔；较长预约用分层取样。报告带符号误差、绝对误差 P50/P95/P99/P99.9、最大值、超过 1/5/10 ms 的次数、漏发/重复、CPU 与电源条件。失败和缺失样本纳入分母，不能只统计成功结果。

覆盖场景：空闲、CPU/磁盘/网络负载、视频播放、窗口最小化/遮挡、笔记本交流/电池、节能状态、多显示器、不同处理器核心布局，以及至少两台不同硬件机器。用 ETW/WPR/WPA 在异常时分析线程抢占、DPC/ISR、硬缺页等原因。

### 11.3 网络时钟的长期验证

记录至少 24–72 小时原始样本，覆盖多次独立启动、不同时间段、网络空闲/拥塞、有线/Wi-Fi、断网恢复。对每次重新对时记录收敛时长、偏差差异和来源变化。

分层验证：

| 级别 | 方法 | 能证明什么 |
|---|---|---|
| A：内部回放 | 模拟服务器，真值已知 | 算法实现和误差估计是否正确 |
| B：留出来源 | 校时使用 A 组来源，B 组只观察，不参与拟合 | 独立来源一致性；仍受公网路径偏差影响 |
| C：可追溯局域网参考 | 有校准信息的 GNSS 驯服时钟、硬件时间戳 NTP/PTP，与被测机建立已知误差的时钟比较 | 量化 UTC 校时偏差，精度取决于整条比较链路 |
| D：端到端外部参考 | 与 GNSS PPS/参考时钟对齐的硬件捕获，或经过校准的目标系统测量接口 | 在规定参考点上测量真实触发时刻；需计入捕获和接口延迟 |

不能把同一批 NTP 源既用于校时，又作为“真实 UTC”自证；不能用另一台未经校准的电脑或普通 USB 串口 PPS 到达时间当作微秒/毫秒真值。C/D 级方案必须列出参考设备、校准状态、接线和误差预算；没有这些条件只能声明 A/B 级验证。

24–72 小时报告应包含时钟偏差时序、误差包络覆盖情况、重新同步前后差异、漂移估计和可选 Allan/TDEV 稳定性指标。稳定性好和绝对偏差小分别下结论。

### 11.4 初始验收目标

| 项目 | 建议验收目标 |
|---|---|
| 任务正确性 | 测试中无重复 down、无已过任务误触发，部分失败明确报告，正常取消释放完整 |
| 本机调度 | 在明确的基准硬件和负载条件下，以 `P99.9(|J_call|) ≤ 1 ms` 为优化目标，最大值和失败率必须公开 |
| 时钟质量 | 按环境实测报告 E_clock；普通公网不预先承诺固定 ±1 ms |
| UTC 端到端 | 只有具备可追溯独立参考并完成误差预算后，才判断是否达到目标 1 ms |
| 故障退化 | 来源不足、时钟异常、误差超预算、会话变化时按策略阻止任务，不维持虚假“已精准同步”状态 |

一个示例预算：时钟估计 0.6 ms、调度统计指标 0.3 ms、调用/观测额外预算 0.1 ms，总计已达到 1.0 ms。若加入目标应用处理还需额外预算。实际分析须明确每项参考点，避免重复计入同一延迟；统计分位数之和也不能未经验证就当作联合 P99.9 保证。

## 13. 首批交付范围和实施顺序

**M0：先验证时钟与调度可行性。** 交付可运行的命令行诊断入口、多源样本日志、初版误差预算和本机空动作调度基准。以目标电脑的数据确定保护窗口、优先级策略及公网可达到的时钟质量。

**M1：实现稳定时钟核心。** 完成 NTP 校验、来源分组、低延迟滤波、多源共识、频率拟合、连续时钟、保持运行和故障状态；通过模拟/回放测试。源目录和每源限速是这一阶段的正式组成部分。

**M2：实现 GUI 和定时输入。** 交付中文界面、手动/自动同步、进度、时间规范化、单键/点击/组合键、有限循环和混合序列、取消与日志。加入可选 Windows 系统校时入口。

**M3：验收与 x64 发布。** 完成真实输入探针、多硬件负载测试、24–72 小时网络观察，输出指标和限制；生成便携 `Ctimer.exe`、配置说明、测试报告与可复现构建说明。

后续增强：NTS、网络硬件时间戳、局域网 GNSS/PTP 接入、目标软件专用延迟标定、独立按键释放看护进程、完整闰秒时间轴。若 M0 证明公网误差已大于预算，应先更换时间参考条件，再继续优化本机微秒级开销。

第一版不承诺：后台任意窗口注入、锁屏/安全桌面执行、任意脚本的毫秒精度、目标应用实际业务完成时间、互联网服务端接收时刻，以及普通 Windows 下绝不超时。
