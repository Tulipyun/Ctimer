# Ctimer v0.1.0 初始版本测试报告

日期：2026-09-28。该报告描述当前初始版本，不能代替生产环境长期精度验收。

## 构建与环境

- Windows 11 专业版，10.0.26200，x64。
- Intel Core i5-9500T，2.20 GHz，6 核 / 6 逻辑处理器。
- LLVM/MinGW-w64 20260922，Clang 23.1.2，C++20、`-O2`、静态 C++ 运行库。
- PE 检查：`IMAGE_FILE_MACHINE_AMD64`、64-bit、Windows GUI 子系统；未依赖 .NET、Qt 或单独的 C++ 运行库 DLL，只导入 Windows 系统组件和系统 UCRT。
- 最终 exe：1,865,216 字节。
- SHA-256：`CF69A20C4EC4BE200F98BE74ABB5E0CB536E654013BA2C1987FE75D28FEBA6E1`。
- 本次只验证一台电脑与一个 Windows 版本，未覆盖多硬件、电池/节能场景或 24–72 小时稳定性。

- 三位毫秒解析；四位、越界和非法输入拒绝；不进行毫秒进位。
- QPC/UTC 映射和频率校正；截止计数向上取整；60 秒保持期间的误差增长。
- 来源配置、禁用、端口、重复地址、最小轮询间隔和 UTF-8 配置写入/加载。
- 完整点击计划、组合键、非法功能键和重复按键拒绝。
- NTP 时间戳转换、2036 回绕、四时间戳偏差/RTT、响应匹配、未同步状态和 KoD。
- 多数来源选择、运营者去重，以及不会因重复采样缩小系统性 RTT 误差预算。
- 频率拟合的已知真值测试。
- **真实 localhost UDP 服务**：模拟服务器人为快 12 ms，验证网络查询和估计应用。
- **真实线程冻结竞争测试**：目标在约 60.15 秒后，进入前一分钟后停止同步且模型不变；冻结中拒绝恢复同步；取消无需等待一分钟。
- **晚到响应测试**：模拟服务器延迟响应，冻结发生在响应完成前，验证该响应无法校准或修改时间模型。

自动冻结检查中的长任务均在测试结束前取消，没有向其他软件发送输入。

## 本机等待调度基准

方法：调用与执行线程相同的 `preciseWait`，高分辨率相对等待定时器 + 最后约 1 ms 的 QPC 自旋，`THREAD_PRIORITY_HIGHEST`，10,000 个计划时刻，间隔 5 ms。运行于普通交互桌面，未隔离后台系统负载。

测量量为“等待函数返回后读取 QPC”相对计划 QPC 的延迟；**不包括 SendInput 调用，不测量真实 UTC 或目标应用处理时间**。

| 指标 | 结果 |
|---|---:|
| 样本数 | 10,000 |
| P50 | 0.0016 ms |
| P99 | 0.0160 ms |
| P99.9 | 2.5617 ms |
| 最大延迟 | 4.4917 ms |
| 超过 1 ms | 13 次，0.13% |

结论：大多数等待具有较低延迟，但这次测试**没有达到 P99.9 ≤ 1 ms**。不能用中位数或 P99 代替最差值，也不能由此承诺硬实时上限。下一轮优化应增加 ETW 调度/中断证据，并在可复现负载条件下比较保护窗口和优先级方案。

早期的 1,000 次普通优先级预检曾得到 P99 0.0166 ms、P99.9 1.0336 ms、最大 1.8841 ms，2 次超过 1 ms。它和最终 10,000 次测试的条件、样本量不同，不用于宣称某个优化必然更好或更差。

## 完整真实输入测试

运行最终 exe 的 `--input-smoke-test`，任务限定到程序自己的前台窗口，输入为 F8，按住设置为 20 ms。独立测试配置没有开启公网 NTP；这里不验证绝对时间。

- 收到 key-down：1 次。
- 收到 key-up：1 次。
- SendInput 插入与释放数量均为 1。
- down 调用前 QPC 相对计划截止：**+0.1834 ms**。
- down 的 SendInput 调用耗时：**1.0300 ms**。
- 测试窗口观测 down/up 的处理间隔：**18.8029 ms**。
- 测试结果：通过。

窗口处理间隔包含两条消息各自的排队与处理延迟，不等于底层按键保持时长。实现从 down 调用返回之后等待至少配置的 20 ms 再提交 up；测试日志也记录了调用前后和释放后的 QPC。不能把调用开始、调用返回或窗口处理时间互相替代。

这是一次真实输入功能验收，不能用单次结果估计长期 SendInput P99.9。鼠标事件计划通过自动检查，但本次未对真实鼠标 down/up 做外部硬件观测。

## 公网 NTP 与 GUI 检查

内置的 Cloudflare、NICT、NIST 在当前网络获得了有效响应。首轮 UI 测试期间的示例 RTT：

| 来源 | 已观测 RTT 示例 |
|---|---|
| Cloudflare | 179.305、185.306、187.082、191.675 ms |
| NICT | 145.003、177.268、189.594 ms，另有超时 |
| NIST | 197.881、212.416、213.610、250.933 ms |

这些是该网络、该时段的观测，不能代表服务在其他网络上的延迟。界面显示过约 ±115–144 ms 的工程误差估计，并明确标记未完成 UTC 独立验证；没有把稳定显示误认为已达到 ±1 ms。

通过 computer-use 对实际 Win32 窗口进行检查，确认主界面布局、来源列表、三位毫秒输入、时间预览、手动停止同步和来源编辑器均可显示/操作。发现原先选用的 F12 全局热键不合适后，已改为 Ctrl+Alt+F10，并在最终窗口确认注册成功；备用为 Ctrl+Shift+F11。

## 当前限制和下一步

1. **绝对 UTC 精度尚未独立验证**。需要更近的时间源、可追溯局域网参考或硬件时间戳，以及明确比较链路。
2. **调度存在超过 1 ms 的尾延迟**。需要记录 ETW 并定位抢占、DPC/ISR、硬缺页等原因。
3. 残余漂移 30 ppm 为初始工程假设，60 秒保持额外预算为约 1.8 ms；未完成当前硬件长期频率标定。
4. 源策略、网络路径变化、长期断网保持和多硬件兼容性需要更长时间测试。
5. 初始版本不含混合脚本编辑器、系统时间写回、NTS、网络硬件时间戳、完整渐调与闰秒控制；交付范围以 README 为准。

本次交付的是可运行、可测量且会暴露精度限制的初始版本。后续应以原始记录和独立参考决定改进优先级。
