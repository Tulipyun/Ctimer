# v0.4 测试与变更记录

日期：2026-09-28。平台沿用 Windows 11 x64 / Intel i5-9500T。

## 已实现

- 分、秒、毫秒独立数值输入；分秒左补零，毫秒作为小数秒右补零，缺省为零。
- 默认鼠标左键；普通与精简窗口、置顶、带符号误差和 UTC 推定不确定度。
- 主界面简化为时间、操作和控制；移除 90 秒后和 F8 测试按钮，诊断仍保留在测试入口。
- 有效配置自动保存，实际启动恢复；每小时循环，成功后自动预约下一小时。
- 默认自动校时、提前 60 秒冻结、准备提示音、操作结束后恢复同步；显式手动暂停保留。
- 自动请求 Windows 管理员授权；具备权限时自动写回系统时间，冻结期间阻止写回。
- 约 10 秒校时周期；多源一致性检查后优选，运营商别名合组，主用来源排在列表首行。
- 同步状态和上次成功时间；失败轮次不再把旧样本重新标记为同步成功。

## 自动检查

76 项检查全部通过。覆盖数值补齐、时间模型、NTP 协议、源选择、冻结竞争、迟到响应、取消、自动恢复、配置持久化和失败状态。

系统时间写回测试使用注入的模拟写回接口，确认成功同步可调用写回、冻结期间和晚到响应不能调用写回。没有修改宿主机时间来运行测试；Windows UAC 与真实权限授予需要用户操作，不由 UI 自动化代为确认。

在随后切换到正式配置、用户完成管理员授权后，正式程序显示“本机已对齐”；观察到本机 − NTP 推定时间为 +0.571 ms，UTC 推定不确定度约 ±36.8 ms。前者验证本机与程序时间基准的对齐，后者仍保留公网不确定度；未宣称真实 UTC 已达到亚毫秒精度。

## 实际 GUI 流程

使用本地 UDP NTP 服务和本程序自己的前台窗口：

- 自动填写三栏后自动预约：通过。
- 准备状态通知：1 次。
- 真实 F8 down/up：各 1 次。
- 按下/释放后恢复同步：通过。
- 成功后自动预约下一小时：通过。
- 两次 NTP 查询间隔：10.074 秒。
- 实际关闭再启动，恢复保存时间 20:30.467 和键盘操作，自动进入预约：通过。

测试中的具体时间是临时自测设置，并未写入用户发布目录的配置。界面自测只向自己的前台窗口发送输入，焦点离开时取消；早期自测因焦点不在窗口或界面连接重置而未发送按键，恢复前台后完整流程通过。

## 时间源核查

阿里云官方文档明确列出供非阿里云实例使用的公网域名，包括 ntp.aliyun.com 和 ntp1–ntp7.aliyun.com。本版本新增三个候选节点；同一运营商只有一组投票。

| 来源 | 本次单轮 RTT |
|---|---:|
| ntp.aliyun.com | 40.2396 ms |
| ntp1.aliyun.com | 33.5337 ms |
| ntp2.aliyun.com | 41.4423 ms |

这不是时间源长期性能排名。选择还参考上游误差、抖动、失败与多源一致性；最接近本地时间的样本不一定准确。

资料：

- [阿里云 NTP 配置及公网服务器表](https://help.aliyun.com/zh/ecs/user-guide/alibaba-cloud-ntp-server)
- [Cloudflare NTP](https://developers.cloudflare.com/time-services/ntp/)
- [NICT 公共 NTP](https://jjy.nict.go.jp/tsp/PubNtp/index-e.html)
- [NIST 时间服务器及频率限制](https://tf.nist.gov/tf-cgi/servers.cgi)
- [TUNA 官方说明源文件](https://github.com/tuna/tuna.github.io/blob/master/_pages/help/ntp.md)：说明涉及清华校内与校园网认证，因此没有将其加入本版本通用默认列表。

保留用户已有腾讯节点并按腾讯组去重。本次未充分核实其当前官方公开服务说明，没有把它们另行标为经过独立认证的默认来源。

## 验证边界

本轮验证的是功能、状态机、保存恢复和可用性，没有重新完成多硬件、24–72 小时 UTC 精度验收。v0.1 的长期等待基准和公网误差限制仍有效，详见初始版本测试报告。UTC ± 数值为工程估计；没有独立可追溯参考时不声明真实 UTC 已达到 ±1 ms。
